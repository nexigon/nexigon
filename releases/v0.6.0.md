# Nexigon Agent and CLI 0.6.0

Unreleased.

## Channel Capacity

Agent 0.6 defaults to 512 multiplex channels. It advertises 480 channels for
forwarding, leaving 32 available for RPC, commands, terminals, and control work.
Hub 2026.3.2 uses the lower of its configured limit and the advertised Agent
capacity as the active device HTTP proxy limit. It applies the lower of its
configured limit and a legacy cap of 24 to older Agents, which do not advertise
capacity. Older Hubs ignore the metadata and retain their existing forwarding
limit.

When a peer exceeds the configured channel-open rate, Agent 0.6 rejects that
channel request and keeps the multiplex connection alive.

### Upgrade Order

Upgrade a Hub to 2026.3.2 before upgrading its Agents to 0.6. The Hub keeps the
legacy device HTTP proxy cap of 24 for older Agents, then negotiates the effective
limit when an upgraded Agent reconnects and announces its capacity.

### Capacity Configuration

Keep the defaults unless a device has tighter file-descriptor or local-service
concurrency limits:

```toml
[multiplex]
max-channels = 512
reserved-channels = 32
max-channel-requests-per-second = 2048
```

`max-channels` must be between 32 and 4096. `reserved-channels` must be positive
and lower than `max-channels`. It reduces the advertised forwarding capacity but
does not partition transport channels by feature.

`max-channel-requests-per-second` must be between 32 and 65536 and at least as
large as `max-channels`. This allows a full-capacity channel-open burst without
triggering the Agent's rate limiter.

Nexigon-provided systemd units set an open-file limit of 8192 for the default
capacity. Custom service definitions must provide enough file descriptors for the
configured capacity and the Agent's other work. The transport scales each
channel's receive window so aggregate advertised byte credit remains bounded at
64 MiB per connection.

## TCP Forwarding Policy

Agent 0.6 permits TCP forwarding only to explicitly configured localhost ports.
HTTP exports authorize their own ports. Additional ports require an enabled
forwarding allowlist. With no exports and no enabled allowlist, all TCP
forwarding is denied.

Both exports and the additional allowlist permit raw TCP access, including CLI
forwarding. An export's HTTP protocol and URL path do not restrict traffic on
that port. Setting `forwarding.enabled = false` disables only the additional
allowlist; exported ports remain accessible.

Forwarding destinations are individual ports from 1 through 65535 on
`127.0.0.1`. Wildcards and ranges are not supported. Hub permissions continue to
apply. Generating a URL does not change the device's policy.

## Migrating from Agent 0.5

Before restarting the new Agent, configure every required port. Existing HTTP
exports already permit their declared ports. Enable the additional allowlist
for other services, such as SSH:

```toml
[[exports]]
name = "Web UI"
protocol = "http"
port = 80

[forwarding]
enabled = true
allowed-tcp-ports = [22]
```

Deploy the new binary and configuration together, then restart the Agent.
Verify each required remote connection after the device reconnects. Missing or
empty allowlists grant no additional ports.

## Compatibility and Rollback

The base forwarding protocol is unchanged. Capacity metadata uses the existing
optional multiplex Hello field, which older peers already ignore. Remote terminal
sessions and commands retain their separate feature toggles; the browser terminal
does not require forwarding port 22.

Older Agents do not enforce the forwarding policy. Rolling back the binary
restores their previous forwarding behavior. Keep the 0.6 configuration so the
policy takes effect when 0.6 is installed again.
